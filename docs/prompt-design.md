# プロンプト設計の記録（prompt-design）

**プロンプト本文はここに書かない。正典は `src/lib/prompts/feedback.ts`。**
本文が知りたい人はそのファイルを読む。ここに書くのは**設計判断だけ**。

二重管理を避けるための構造。本文をコピーすると、必ず片方が古くなる。

関連：確定値は `docs/spec.md` §10、判断の索引は `docs/decisions.md`。

---

## 1. なぜ cause をアプリ側で確定させてから渡すのか

**AI に原因を「分析」させない。** `cause` は `src/lib/diagnosis.ts` が確定済みの事実として渡し、
AI の役割は「確定した原因を鈴木さんの言葉で説明する」ことに限定する。

普通の実装は原因推定まで AI に丸投げするので、返ってくるのは一般論になる。
このアプリは誤答の選択肢を設計段階で作り分け（誤答A＝異なる品詞／誤答B・C＝同じ品詞）、
どれを選んだかで原因が決まる。だから AI は推測する必要がなく、**必然的に個別化される**。

これは評価項目1「必要な情報をセットで渡せているか」への直接の答えでもある。

**この設計がこのアプリの唯一の売り。プロンプトでこれを壊してはいけない。**
「原因を分析してください」と書いた瞬間に、他のアプリと同じものになる。

## 2. なぜ causeCounts を渡すのか（AI に数えさせない）

原因ごとの件数はアプリが数えて渡す。AI に数えさせない。

`pattern_summary`（今日の傾向）は「品詞の取り違えが3回」のような数字を含む。
ここを間違えると、鈴木さんが読んだ瞬間に信用を失う。
数え間違いは文章の説得力を直撃するので、**数えられるものはアプリが数える**。

同じ理由で `is_instant`（即答判定）もアプリ側で済ませて真偽値で渡す。
閾値（テンポ設定）を AI に渡して判定させると、境界の扱いがぶれる。

## 3. なぜ cause_label をスキーマから外したのか

`cause_label` は `cause` から一意に決まる日本語表記（例：`pos_mismatch` → 「品詞の取り違え」）。

AI に生成させると、呼び出しごとに「品詞の間違い」「品詞のミス」などと文言が揺れる。
**同じ原因が別物に見えると、復習カードを並べたときに分類として機能しない。**

レスポンススキーマから消してあれば、揺れる余地が構造的にゼロになる。
「AI に返させて捨てる」形にしなかったのは、後から読んだ人に
「なぜ捨てているのか」を毎回問わせる構造になるため。

出力トークンとレイテンシが5枚分減る副次効果もある。

実装は `src/lib/diagnosis.ts` の `CAUSE_LABEL` / `causeLabel()`。
`Cause` 型を所有しているモジュールに置き、Cause を扱う場所を1箇所に保つ。

## 4. なぜ出力を5枚に絞ったのか

復習対象は2カテゴリ（誤答／非即答正解）で、10問中最大10語に達しうる。
これに pending（前回埋まらなかったカード）最大5件が加わるので、
上限を設けないと**1回で15枚**を要求しうる。

15枚はレイテンシが読めない。結果画面の `analyzing` は「唯一の演出箇所」だが、
待たせすぎれば演出ではなく苦痛になる。鈴木さんは通勤電車で使う。

優先順位は **pending → 今回の誤答 → 今回の非即答正解**。
pending を先に消化することでバックログの累積を防ぐ。
欠けた語は pending のまま残り、次回の呼び出しで埋まる（部分充足を許容する設計）。

**枚数は二重で担保する。** JSON Schema の `maxItems` が structured outputs で
使えないため、プロンプト本文での明示（`src/lib/prompts/feedback.ts`）と
アプリ側の `slice(0, 5)`（`src/lib/aiResponse.ts`）の両方で守る。

## 5. なぜ structured outputs を使うのか

JSON スキーマを強制し、**パース失敗で AI 経路が死ぬのを防ぐ**。

自由文で返させて正規表現で切り出す方式は、モデルが説明文を足した瞬間に壊れる。
壊れたときに何が起きるかというと、鈴木さんの画面が真っ白になる。

`output_config: { format: { type: "json_schema", schema } }` を使う。
旧 `output_format` パラメータは非推奨。

制約が3つある。

- 全オブジェクトに `additionalProperties: false` が必要
- `maxLength` / `minLength` / `maxItems` / `minimum` / `maximum` は非対応
  → 枚数と文字数はプロンプト本文とアプリ側で担保する
- `enum` と `anyOf` は使える → `suggested_tempo` は4値 enum で表現した

## 6. なぜ suggested_tempo を必須の4値 enum にしたのか

`"slow" | "normal" | "fast" | "none"` の4値、かつ `required`。

「省略できる」形にすると、**省略が意図的だったのか出力漏れだったのか区別できない。**
変更不要なら `"none"` を明示させる。

AI の提案はそのまま適用しない。`src/lib/aiResponse.ts` が数値条件を**再計算して**検証し、
満たさなければ黙って捨てる（レスポンス全体は捨てない）。

これで「AI の出力が実際にアプリの挙動を変える（＝独自性）」と
「AI に推測させない（＝設計原則）」を両立させている。

`"normal"` だけは定性条件（「現テンポが明らかに不適合」）で再計算できる数値がないため、
条件2（現テンポと異なる値）のみを確認して通す（spec.md §10-4）。

## 7. 渡さないものと、その理由

| 渡さないもの | 理由 |
|---|---|
| 日付 | 学習内容と無関係。プロンプトに入れると同じ入力でも文字列が変わり、純関数性とキャッシュが壊れる |
| localStorage 全体 | 必要なのは今回の10問と pending だけ。全部渡すのは情報漏れであり、トークンの無駄 |
| セッション履歴 | 過去のスコアは今日の説明に不要。AI が過去と比較して励まし始めると、禁止事項2に触れる |
| 個人情報 | そもそも収集していない。認証もDBもない設計 |

`buildFeedbackPrompt()` が純関数であること（`Date.now()` も `Math.random()` も呼ばない）は
テストで固定してある。同じ入力なら必ず同じ文字列を返す。

## 8. 禁止事項を明文化した理由

役割と口調だけでは足りない。「励ましすぎない」と書いても、
モデルは末尾に「頑張りましょう」を付けたがる。

4項目を具体的に禁止した。

1. 原因の推測・言い換え（→ 1 の設計を壊させない）
2. 汎用的な励まし
3. 学習法の一般論
4. 語数・時間・スコアの創作（→ 渡した数値以外を書かせない）

4は評価項目2「汎用的な一般論に留まっていないか」への防御でもある。
数字を創作されると、それが一番目立つ嘘になる。

## 9. テストできる境界

**LLM が返した文章の中身はテストしない。** 出力をアサートすると点滅するテストが生まれ、
それを避けようと緩い判定を書くと「アサーションを緩めない」というルールに抵触する。

代わりに、**何を渡しているか**と**返ってきたものの構造**をテストする。

| テストする | テストしない |
|---|---|
| プロンプトに禁止事項・causeCounts・similar・example_scene が含まれる | explanation の妥当性 |
| プロンプトに日付・localStorage キーが含まれない | 例文の品質 |
| `buildFeedbackPrompt` が純関数（同入力→同出力） | レイテンシ |
| スキーマが非対応キーワードを含まない | |
| 検証層 V1〜V6（幻覚の排除・枚数制御） | |

`src/lib/prompts/feedback.test.ts`（11件）と `src/lib/aiResponse.test.ts`（11件）。

## 10. 検証層を V2 → slice の順にした理由

`slice(0, 5)` を検証より先に行うと、**切り捨てられる範囲に出題していない語があっても
検出されずに素通りする。**

V2 は「AI の幻覚を構造的に防ぐ」ための検証なので、そこに穴を開けない。
6枚目に不正な `id` があれば、レスポンス全体をエラー扱いにして pending 方式に落とす。

この順序は `src/lib/aiResponse.test.ts` の
「★6枚目に不正な id があれば、切る前に全体エラーになる」で固定してある。

## 11. AI が落ちてもアプリが死なない設計

SCORE・正誤・出題・テンポ・履歴はすべてアプリ側の計算なので、AI が落ちても動く。

- APIキー未設定でも 500 を返さない。`{ ok: false, reason }` を 200 で返す
- クライアントは25秒で打ち切る（Route Handler の `maxDuration` は60秒。クライアントが必ず先に諦める）
- 復習カードは pending のまま作られ、次回の呼び出しで説明が埋まる
- 画面のエラー表示は1行だけ。**謝罪文なし。再取得ボタンなし**

再取得ボタンを作らないのは、押したくなって待たされるため。
「説明は次回のセッションで追加されます」は失敗の報告ではなく予定の告知として書く。

## 12. 観察が必要な点：文法的な断定の正しさ（2026-08-16 追加）

**プロンプトはまだ変更していない。観察のためにここへ残す。**

実API疎通（`docs/spec.md` §10-11）で `id=33 discuss` の `explanation` に
「discussは他動詞で、discuss aboutのように前置詞を伴わない点を取り違えた」が返った。

**これは禁止事項1の違反ではない。** 禁止事項1は「原因を覆したり別の原因を提示したりしない」であり、
AI は確定した `pos_mismatch` を覆しておらず、別の原因も出していない。具体化しただけである。

**別のリスクがある。** AI が `explanation` / `usage_note` の中で
文法的な断定（「discuss about とは言わない」等）を行っており、
今回はたまたま正しかったが、**他の語で事実として間違う可能性がある。**

- アプリが渡しているのは `pos` / `meaning` / `similar` / `example_scene` だけで、
  語法・共起・可算不可算などの情報は渡していない。断定の根拠はモデルの内部知識のみ
- **これはテストで守れない。** `CLAUDE.md` のテスト境界どおり、
  LLM が返した文章の中身はテストしない（点滅するテストになる）
- 検証層 V1〜V6 は構造しか見ないので、内容が誤っていても通過する

**観察の方法**：STEP 6 以降で実際に何セットか回し、`usage_note` の断定が
事実として誤っているケースが出るかを目視で見る。

**出たときの対処案（まだ採らない）**：禁止事項に
「渡された情報から確認できない文法規則を断定しない」を足す。
ただし禁止を増やすと文章が痩せて一般論に寄る危険があるので、
実例が出てから判断する。先回りして足さない。
