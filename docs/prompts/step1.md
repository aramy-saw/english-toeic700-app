## 1. 作るもの・想定ユーザー・必須要件

【作るもの】
DMM生成AI CAMP Claude Codeマスターゼミの卒業課題。
アプリ名は「ENGLISH700」。
「TOEIC700点突破を目指す社会人向け英単語アプリ」を生成AI Webアプリとして作る。

【想定ユーザー】
32歳・会社員の鈴木さん。通勤30分＋昼休み15分しか学習時間がない。
過去に英単語アプリを試したが3日で飽きた。
欲しいのは「今日これをやれば確実に前進している」という実感。

【必須要件】
- 配布された300語のJSONを使った出題機能
- Claude APIを使ったフィードバック機能を1つ以上
- 1回のプレイが10問前後で終わる

## 2. 技術スタック（確定済み・変更しない）

- Next.js（App Router）+ TypeScript + Tailwind + Vercel
- API Routes でAPIキーをサーバー側に隠す
- データは src/data/wordlist.json（静的・300語）
- 進捗保存は localStorage
- 認証なし・データベースなし
- AI は Claude API（claude-sonnet-5）。環境変数 AI_MODEL で切替可能にする

## 3. 三層ディレクトリ

- src/lib/       純粋TS。DOMもfetchもしない。テスト対象
- src/lib/prompts/  プロンプト組み立ての純関数。ここがプロンプトの正典
- src/platform/  ブラウザ固有（localStorage・Date.now）
- src/app/       Next.js（画面・API Route）

## 4. 設計方針（確定済み・変更しない）

業界の3課題のうち「②間違えた原因がわからない」に一点集中する。

※①③も §8-3 の形で成立させる。一点集中とは「①③に新機能やコストをかけない」という意味であり、無視するという意味ではない。

出題形式：英単語 → 日本語の意味を4択
（「日本語→英単語」にすると similar が類義語のため両方正解になる）

4択の内訳を意図的に設計し、選んだ選択肢で原因が確定するようにする。
- 正解：出題語の meaning
- 誤答A：異なる pos の語の meaning → 選んだら pos_mismatch
- 誤答B：同じ pos・同じ level 帯の語 → 選んだら weak_memory
- 誤答C：同じ pos・異なる level 帯の語 → 選んだら weak_memory

さらに回答時間を計測する。
- 正解だが即答の閾値を超えた → hesitant（自覚のない曖昧さ）
  閾値はテンポ設定で可変。ゆっくり8秒／ふつう5秒（既定）／はやい3秒。すべて暫定値。
- 無回答・タイムアウト → weak_memory

AI呼び出しは10問終了後に1回だけ。毎問は呼ばない。
理由：待ち時間ゼロ・コスト1/10・AIが10問全体のパターンを見られる。

AIには原因を分析させない。アプリ側で確定させた cause を渡し、
「確定した原因を鈴木さんの言葉で説明する」役割に専念させる。

## 5. ゲーム性（SCORE・テンポ・復習カードと卒業条件・pending方式）

- ポイント・バッジ・レベルアップは採用しない。response_ms から自然に生えるものだけを使う
- SCORE：即答で正解10点／迷ったが正解5点／誤答・無回答0点。10問で100点満点
- テンポ（ゆっくり8秒／ふつう5秒［既定］／はやい3秒）で即答の閾値を可変にする。
  即答率が高いユーザーには、AIが next_message で次回のテンポ変更を提案する
- 復習カード（間違えた語／正解したが即答できなかった語が対象）を localStorage に保存し、
  次回以降その語を「即答で正解」できたら卒業（カード削除）
- AI障害時は pending 方式。説明文が空のカードを作り、次にAIを呼ぶときに
  その回の10問分と一緒に最大5語まで渡して埋める
- 詳細は `ENGLISH700_構想と方針.md` §5-10 を参照

## 6. 配布データの重要な性質（発見1〜3）

- similar は「混同語」ではなく「類義語」。誤答に使うと両方正解の不良問題になる
  → 誤答には使わない。フィードバックの使い分け説明に使う
  → 誤答候補のブロックリストとしては使う
- similar語の88%は300語リスト外。日本語訳が存在しない
- example_scene は300語に対して276種類。グループ化には使えない
  → 例文生成・文脈提示の材料として使う
- pos は「動詞/名詞」のような複合表記が混在する。正規化が必要
- word の値が26語ぶん重複している（同じ英単語が異なる id で2回登場）
  → 誤答候補の word が出題語の word と一致する場合は除外する（id ではなく word で判定）
  → 1セッション10問の中で word が重複しないようにする
  → 詳細は 構想と方針.md §4 発見3
- id は 1〜300 で全ユニーク。JSON のオブジェクトキー重複はゼロ
  （Cursor の JSON リンターが 445/447 行目に出す警告は誤検知）
- src/data/wordlist.json は配布データ。絶対に書き換えない

## 7. サーバー側で計算してはいけないもの（環境の罠/Vercel-Next.js.md）

- 「今日」を Server Component で計算しない。Vercelのサーバーは UTC。
  JST 0〜9時が前日になる。日付はクライアント側で完結させる
- 出題順のシャッフルを Server Component で実行しない。
  ハイドレーション不一致になる。マウント後にクライアントで実行する

## 8. やらないこと

- 認証・ユーザー登録
- データベース（進捗は localStorage）
- 例文の300語ぶん事前一括生成（review_cards で同時に返るため不要）
- **AI に原因を推測させること**
  cause はアプリ側で確定させてから渡す。AI の役割は「確定した原因を鈴木さんの
  言葉で説明する」ことに限定する。原因推測まで任せると一般論が返り、評価項目2で落ちる

## 8-2. デザインの位置づけ（★捨てない）

課題文の「凝ったデザインより Claude API の組み込みで差がつく」は、
**優先順位の話であってデザインを捨てるという意味ではない。**
評価項目4に「UI・操作性」が明記されており、配点がある。

鈴木さんは一度3日で飽きた人。機能が正しくても、触っていて気持ちよくなければ4日目は来ない。

守ること：
- 通勤電車・昼休みに片手で使える。タップ領域は大きく
- 迷わない。テンポが良い。進捗が数字で見える
- 15分で1回分が終わる
- 背景は暗め固定（通勤中・就寝前でも眩しくない）
- 差し色は2色まで。それ以外は抑える
- 色だけに頼らず、文字でも状態が分かる

**凝る場所は1箇所に絞る：AIフィードバックが出る瞬間。**
10問終わって「あなたは品詞の取り違えが3回ありました」と返る、その瞬間。
テキストがドサッと出るだけなら読まれない。ここに手触りがあれば明日も開く。
独自性（評価項目5）もここで主張する。

それ以外の画面は「機能する最低限」で十分。凝る場所を増やすと②が薄くなる。

## 8-3. 3課題への対応（②に一点集中。ただし①③も成立させる）

課題文の3課題すべてに、この設計は答えを持っている。
評価項目3は「少なくとも1つ」を求めているが、②を解く過程で①③も自然に成立する。
新しい機能を足すのではなく、既にある要素で応える。

| 課題 | 対応 | 実装 |
|---|---|---|
| ① 覚えた≠使える | 副次的に応える | review_cards の usage_note（similar で使い分け）と example（example_scene でビジネス例文）。localStorage に保存し、即答できるまで何度でも読める |
| ② 原因がわからない | **正面から解く** | 誤答の構成を設計し cause を確定（pos_mismatch / weak_memory / hesitant）。回答時間も判定材料。AI が鈴木さんの言葉で説明 |
| ③ 実感がない | 数字で成立 | SCORE（即答10点・正解5点）・即答率・テンポ・復習カードが減っていく |

**①③のために専用画面や新機能を作らない。** 例文専用ページ・学習カレンダー・
グラフなどは作らず、既に生成しているデータを見せるだけにする。

## 9. Plan Mode で決めること（チェックリスト）

対話の中で以下を決める。決まったら docs に書かせる。

- [ ] 出題語の選び方（level配分・未学習優先・復習優先のルール）
      ※暫定案：未学習優先 → 過去の誤答語を混ぜる → L1:L2:L3 = 1:4:5
- [ ] テンポ3段階の閾値（暫定8/5/3秒。実装後に自分で触って調整）
- [ ] 画面構成（何画面にするか）
- [ ] localStorage に持つデータ構造
- [ ] AI が返すJSONスキーマ
- [ ] 復習カードの localStorage データ構造と卒業判定
- [ ] pending の扱い（AI障害時）

## 10. 制約

- 推測で書かないこと。読めなかった場合は「読めなかった」と明言すること
- 違っていたら違っていたと明言すること
- 「この方法では見えないもの（限界）」を必ず添えること

まずは要件を確認する質問をしてください。
いきなり実装計画に入らないでください。
