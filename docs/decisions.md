## 1. 課題②に一点集中した（①③は既存要素で成立させる）

業界3課題のうち **②間違えた原因がわからない** を正面から解く。

**理由**：作業時間5〜10時間で3つ全部に手を出すと全部が薄くなる。評価項目3は「少なくとも1つ」を求めている。加えて `pos` が全語にある＝運営が判定材料を先に揃えている＝②をやれというシグナルと読んだ。

**①③を捨てたわけではない。** ②を解く過程で自然に成立する範囲で応える。**専用画面も新機能も作らない。**

| 課題 | 対応 | 使う要素 |
|---|---|---|
| ① 覚えた≠使える | 副次的 | review_cards の usage_note（similar）と example（example_scene） |
| ② 原因がわからない | **正面** | 誤答の構成設計＋cause 確定＋AIの説明 |
| ③ 実感がない | 数字で | SCORE・即答率・テンポ・復習カードが減る |

## 2. 出題形式を「英単語 → 日本語4択」にした

**採用しなかった案**：「日本語 → 英単語」

**理由**：`similar` が類義語なので、日本語→英単語だと選択肢に similar 語を置いた瞬間に「両方正解」になる。

```
「提供する・与える」→ provide / supply / offer / give
```

4つとも正解になってしまう。英単語→日本語なら、日本語 `meaning` の重複だけ管理すればよい（→ 判断4）。

## 3. `similar` を誤答選択肢に使わない

**理由（実測）**：

| 項目 | 数値 |
|---|---|
| `similar` の総出現数 | 860 |
| **うち300語リスト内に存在する出現** | **101（11.7%）** |
| `similar` が1つもリスト内にない単語 | 219 / 300 |

※「101」は**出現ベース**（860出現のうち101回がリスト内の語）。ユニーク語で数えると692語中70語（10.1%）。どちらも同じ事実を別の粒度で見たもの。

つまり `similar` の語の大半には**日本語訳が存在しない**。選択肢として並べることすらできない。

**→ 誤答生成には使わない。フィードバックの「使い分け説明」の材料として使う。**
**→ ただしブロックリストとしては使う**（両方正解を防ぐため）。

補足PDFは `similar` を「混同しやすい類似語」と説明しているが、実物は**同義語**だった。ここを読み違えると設計全体が崩れる。

## 4. ブロック条件5（`meaning` の共通要素）を追加した

**当初の4条件では防げない「両方正解」が6組残っていた**（実測）。

| 出題語 | 誤答候補になりうる語 | 共通する意味 |
|---|---|---|
| 26 announce「発表する・告知する」 | 28 present「発表する・出席している」 | 発表する |
| 63 coordinate「調整する・まとめる」 | 158 calibrate「較正する・調整する」 | 調整する |
| 73 facilitate「促進する・容易にする」 | 205 stimulate「刺激する・促進する」 | 促進する |
| 73 facilitate | 223 expedite「促進する・迅速に処理する」 | 促進する |
| 205 stimulate | 223 expedite | 促進する |
| 260 upfront「前払いの・率直な」 | 267 forthcoming「今後の・率直な」 | 率直な |

**6組すべてが同じ主要品詞**なので、誤答B・誤答Cの候補として実際に選ばれる。

**これは単なる不良問題ではない。** 出題語が `facilitate` のとき誤答に `expedite` が出ると、鈴木さんが「促進する」を見て迷うのは**正しい判断**であり、それを `weak_memory`（記憶が薄い）と診断するのは**誤診断**になる。本アプリの唯一の売りが「原因が確定すること」なので看過できない。

**実測した追加コスト：**

| | 平均ブロック数 | 誤答Aが空 | 誤答Bが空 | 誤答Cが空 |
|---|---|---|---|---|
| 4条件 | 1.73語/出題語 | 0語 | 2語 | 1語 |
| **5条件（採用）** | 1.77語/出題語 | 0語 | 2語 | 1語 |

バケットが空になる語は**1語も増えない**。実質タダで6組の誤診断を防げる。

## 5. 複合品詞は「先頭トークン」を主要品詞とする

`pos` には「動詞/名詞」のような複合表記が35語ある。誤答A「異なる pos」の判定方法が仕様書に未定義だった。

**採用**：正規化後の**先頭トークンのみ**で判定する。

**理由1**：「動詞/名詞」15語と「名詞/動詞」11語が**別々に存在する**＝作成者が主要用法を先に書いていると解釈できる。`meaning` の語順とも一致する。

**理由2**：全トークン交差方式（複合語を広く同一視する）は、**名詞と動詞の区別＝まさに `pos_mismatch` で測りたいものを潰す**。

**理由3（実測）**：誤答が組めない語の数

| 判定方法 | 誤答が組めない語 |
|---|---|
| **先頭トークン（採用）** | **2語** |
| 全トークン交差 | 7語（名詞句6語の誤答Cが全滅） |

先頭トークン方式のほうが精度も供給量も優れている。

## 6. 復習カードのキーを `id` にした（`word` ではない）

**採用しなかった案**：`word` をキーにして同じ英単語を1枚に統合

**理由**：配布データに `word` 重複が26語ある。同じ綴りでも意味が全く違う組がある。

```
overhead (121) 経費・間接費
overhead (287) 頭上の・上空の
```

`word` をキーにすると、「経費」の意味を覚えただけで「頭上の」も卒業扱いになる。**覚えていない語が復習対象から消える**のは、このアプリで最も避けたい事故。

`mutual`(192「相互の・共通の") と `mutual`(279「お互いの・双方の」) のように意味が近い組もあるが、**判定を単純に保つため一律で id 別カード**とする。

## 7. AI呼び出しを「10問終了後に1回だけ」にした

**採用しなかった案**：1問ずつ呼ぶ

| | 1問ずつ | 10問まとめて（採用） |
|---|---|---|
| 待ち時間 | 毎問発生 | ゼロ |
| APIコスト | 10回 | 1回 |
| **AIが見える範囲** | その1問だけ | **10問全体のパターン** |

**3つ目が本命。** まとめて渡すと「今日は品詞の取り違えが3回。動詞の名詞形で崩れる傾向がある」という**パターンレベルの指摘**ができる。1問ずつだと点の指摘しかできず、評価項目2が警戒する「汎用的な一般論」に落ちる。

鈴木さんは通勤電車で使う。毎問2〜3秒待たされたら、また3日で終わる。

## 8. AIに原因を推測させない

`cause` は**アプリ側で確定させてから渡す**。AIの役割は「確定した原因を鈴木さんの言葉で説明する」ことに限定する。

**理由**：普通の実装は原因推定までAIに丸投げするので一般論が返る。原因を先に確定させれば**必然的に個別化される**。評価項目1「必要な情報をセットで渡せているか」への直接の答えでもある。

同じ理由で `causeCounts`（原因ごとの件数）も**アプリが数えて渡す**。AIに数えさせると数え間違いが `pattern_summary` の説得力を直撃する。

`suggested_tempo` も同様に、AIの提案をアプリ側が**数値条件で再計算して検証**し、満たさなければ黙って捨てる。

## 9. モデルを `claude-sonnet-5` にした

**当初の指定**：`claude-sonnet-4-6`

**変更理由**：`claude-sonnet-4-6` は**前世代のSonnet**であり、**structured outputs の対応モデル一覧に含まれていない**（対応：Fable 5 / Opus 5 / Opus 4.8 / Sonnet 5 / Haiku 4.5）。JSONスキーマ強制は本設計の根幹（AI経路がパース失敗で死ぬのを防ぐ土台）なので、非対応モデルでは成立しない。

**Sonnet を選ぶという判断自体は変えていない。世代だけ現行に上げた。**

**API上の制約（実装時に効く）：**

- スキーマ強制は `output_config: { format: { type: "json_schema", schema } }`。旧 `output_format` は非推奨
- 全オブジェクトに `additionalProperties: false` が必要
- `maxLength` / `maxItems` / `minimum` などは**非対応**。「1〜2文で」「最大5枚」はプロンプト本文で指示する
- `temperature` / `top_p` / `top_k` は非デフォルト値を渡すと**400エラー**
- adaptive thinking がデフォルトON。`max_tokens` は thinking と本文の合算上限

環境変数 `AI_MODEL` で切替可能にしてあるので、遅ければ Haiku 4.5 と実測比較して切り替える。

## 10. 例文の事前一括生成を破棄した

**検討した案**：300語ぶんの例文を事前生成してJSONに焼く

**破棄した理由**：本設計では例文が `review_cards[].example` として**同じ1回の呼び出しで返る**ため不要。事前生成スクリプトを書く時間（約1時間）がまるごと浮く。

`example_scene` は300語に対して276種類あり、グループ化には使えない（実測）。例文生成・文脈提示の材料としてのみ使う。

## 11. 画面を「単一ページ遷移」にした

ホーム・出題・結果を `/` 内の React state 遷移にし、`/review` だけ別ルートにする。

**採用しなかった案**：`/`・`/quiz`・`/result`・`/review` をすべて別ルート

**理由**：セッション状態（出題語・回答・経過時間）を localStorage に中間保存する必要がなく、ハイドレーション不一致の考慮も減る。別ルートにすると Context か localStorage で状態を持ち回す必要があり、リロード時の復元も考えることになる。

**代償として、セッション途中で離脱すると結果が消える。** 1セット3〜5分なので実害は小さいと判断した（→ §15 限界）。

## 12. 問題数を定数化した（UIに選択肢は出さない）

```ts
export const QUESTIONS_PER_SESSION = 10;
export const LEVEL_RATIO = { 1: 1, 2: 4, 3: 5 };
```

**コードのどこにも数値 `10` を直書きしない。** level配分も比率として持ち、問題数から枠数を算出する。

**理由**：提出版は必須要件どおり10問固定。ただし提出後の自分用カスタム版では20問にしたい。**定数1行の変更で済む構造**にしておく。

実測で 20問→2:8:10 に自動追従することを確認済み。

**UIに問題数の選択肢は出さない。** 選ばせると「何問がいいか」を考える手間が増え、スキマ時間で迷わず使うという要件に反する。

## 13. 「もう1セット」を入れた（問題数は可変にしない）

結果画面に「もう1セット」ボタンを置き、押すとセッション状態をリセットして新しい10問が始まる。

**理由**：

- 必須要件「1回のプレイが10問前後」は守る。**問題数を可変にはしない**
- 「もっとやりたい」は**問題数ではなく回数**で満たす
- 1セットごとに SCORE が出るので、**記録の比較可能性が保たれる**（2セット合算だと200点満点になり過去の100点満点と比較不能）
- 単一ページ遷移なので実装は状態リセットのみ

**セッション履歴は1セット＝1レコード。** AI呼び出しも1セット＝1回（もう1セットすれば2回目が発生する）。

前セットで出た語は除外しない。むしろ前セットで落とした語はカードができて優先度が上がっているため、2セット目に再登場して**そのセットで卒業できる**。これは「今日これをやれば前進している」実感に直結する意図した挙動。

## 14. アプリ名を ENGLISH700 にした

| 観点 | 判断 |
|---|---|
| 何のアプリか | 一目でわかる。審査員が数分で見る前提では明快さが最優先 |
| 課題文との一致 | 「TOEIC700点突破を目指す社会人向け」そのもの |
| 弱み | アプリの核（正誤の外側を見る仕組み）が名前に入っていない |

**弱みは `<title>` とトップページのタグラインで補う。** 名前で説明しきろうとせず、名前は指し示すだけにする。

## 15. 端数配分に最大剰余法（ハミルトン方式）を採用した

`LEVEL_RATIO = 1:4:5` は10問なら割り切れるが、問題数を変えると端数が出る（15問なら 1.5 / 6 / 7.5）。

**採用**：最大剰余法。小数部の降順に1枠ずつ配り、**同値のタイブレークは level の降順（L3 → L2 → L1）**。

**タイブレークをL3優先にした理由**：目的がTOEIC700突破であり、L3は150語＝プール最大かつ伸びしろが大きい。端数を易しい側に寄せると「今日やった手応え」が薄れる。L1は40語しかなく、枠を増やすと枯渇が早い。

実測結果：

| 問題数 | L1 | L2 | L3 |
|---|---|---|---|
| **10（提出版）** | 1 | 4 | 5 |
| 12 | 1 | 5 | 6 |
| 13 | 1 | 5 | 7 |
| 15 | 1 | 6 | 8 |
| **20（自分用）** | 2 | 8 | 10 |

## 16. 自作語の id は 1001 番台から

```ts
export const DISTRIBUTED_ID_MAX = 300;
export const CUSTOM_ID_BASE = 1001;
```

**採用しなかった案**：文字列キー（`"dist:12"` / `"custom:1"` など）

**理由**：

1. `WordId = number` のまま維持できる。文字列キーにすると配布JSONの `id: number` を毎回変換する層が要り、localStorage に既に書いた値との互換も壊れる
2. 1000 という境界に意味を持たせられる（`id < 1000` = 配布データ＝書き換え禁止、`id >= 1001` = 自作）。ログや復習カードを見た瞬間に出所が分かる
3. 1001 開始（1000 ではなく）で境界値のオフバイワン議論を避ける
4. 自作語は `src/data/custom-words.json` を新規作成して concat する。**配布ファイルは一切触らない**という制約を構造で守れる

**提出版では自作語を追加しない**（時間予算）。方針だけ確定させておく。

## ★未確定（実装後にここへ追記する）

### テンポ閾値 8 / 5 / 3 秒

| テンポ | 即答の閾値 |
|---|---|
| ゆっくり | 8秒（暫定） |
| ふつう | 5秒（暫定・既定） |
| はやい | 3秒（暫定） |

**この3つの数字には現時点で根拠がない。**

「TOEIC Part 5 は1問あたり約20秒、文法と文脈読解を含むので単語の意味想起に使える時間は3秒程度」という理屈は立てたが、**実測はしていない**。

閾値は SCORE・復習カードの卒業判定・`suggested_tempo` の発火条件すべてに効く中心的なパラメータなので、**実装後に自分で触って調整し、確定値と根拠をここに追記する**。

調整時に見るべきもの：

- 「ふつう」で自分の即答率が何%になるか（低すぎると常に迷い扱いになり卒業できない）
- 「はやい」が実際に達成可能か（不可能なら AI が提案しても意味がない）
- 通勤電車の揺れる環境でタップが遅れる分をどう見るか
